# Self-hosting operations guide

This guide describes how to run `dev-orch` against the repository that owns the
framework. It is an operational guide for local, isolated runs; it does not
grant permission to change protected paths or perform remote or production
actions.

## Prerequisites and preflight

Run commands from the repository root. Before the first run, confirm:

- Git is available and the base checkout is clean. A run records the current
  commit and refuses to bootstrap from a dirty checkout.
- The local Python environment and configured provider binaries are available.
  Run `dev-orch doctor` and resolve failed environment or repository-contract
  checks before proceeding.
- The repository has a prepared project configuration and the required contract
  files described below.
- The request has one or more explicit acceptance criteria. Criteria are what
  final verification must judge, so make them meaningful and testable.

The project scope currently permits `src/`, `tests/`, `docs/`, `README.md`, and
`pyproject.toml`. `.ai/`, `.git/`, `.venv/`, `.worktrees/`, and `.superpowers/`
are excluded from agent modification scope.

## Bootstrap

Self-hosting has one narrow, pre-run bootstrap exception. From the prepared
repository, run:

```text
dev-orch init --config <prepared-project.yaml>
```

Initialization creates the repository contract files:

```text
AGENTS.md
.ai/project.yaml
.ai/context.md
```

This initialization happens outside an orchestrated run solely to establish
repository and orchestration policy. `.ai/context.md` is write-once: it is not
regenerated by `--force`. `--force` may regenerate `AGENTS.md` and
`.ai/project.yaml`, subject to their uncommitted-edit safeguards.

Commit all three bootstrap files before the first self-hosted run begins. This
bootstrap mechanism is not an in-run exemption from the scope fence or from
protected-path restrictions.

## Declared project configuration

The framework repository declares:

- project classification: `internal_operating_system`;
- active profile: `agent_orchestration`;
- profile controls requiring plan review, implementation review, final
  verification, and workflow-change review;
- relevant-only prior-artifact loading;
- on-demand plans under `docs/superpowers/plans` and specifications under
  `docs/superpowers/specs`;
- fail-closed handling for conflicting values of the same control supplied by
  active profiles.

`substantial` is a per-run tier, not a project setting in `.ai/project.yaml`.
The classifier can select it, or an operator can request it with
`dev-orch run --tier substantial`. An explicit tier may raise the classified
tier but cannot lower it. Self-hosted runs are not inherently substantial; use
the substantial workflow for work classified or overridden to that tier.

## Context: declared policy versus observed behavior

The declared context policy identifies `AGENTS.md` and `.ai/context.md` as
persistent context and allows relevant on-demand plans and specifications.
That is a context-selection policy, not evidence that every listed file is
currently included in an agent prompt.

The supplied run manifest at `.ai/runs/<run_id>/manifest.json` records
`context_included: []` and records both `AGENTS.md` and `.ai/context.md` in
`context_excluded` because of the scope fence. The assembler evidence in
`src/dev_orchestration/context/assembler.py` likewise enforces stage-specific
context categories and its reference loader rejects paths outside the fence.
Do not assume from the persistent-context declaration that either file reaches
current agent prompts.

The unresolved authority question is therefore explicit: the declared
persistent-context policy claims one behavior, while the runtime manifest and
assembler behavior show another. This guide does not choose a canonical claim
or imply that the gap is fixed. Reconciliation requires a separately approved
change to the relevant canonical documentation, specification, configuration,
or implementation, and is outside this documentation-only change.

Fail-closed context behavior applies specifically when active profiles provide
conflicting values for the same profile control. It is not a general mechanism
for detecting every conflict between context sources.

## Operating a run

Use the CLI flow below as appropriate:

```text
dev-orch doctor
dev-orch init --config <prepared-project.yaml>   # only during pre-run bootstrap
dev-orch run "<request>" \
  --tier substantial \
  --criterion "<specific acceptance criterion>" \
  --criterion "<another criterion, if needed>"
dev-orch status <run_id>
dev-orch runs
```

Always provide one or more `--criterion` values for a substantial run. If
criteria are omitted, the CLI warns that it will verify against the request
text itself; explicit criteria make the acceptance contract auditable.

Execution occurs in an isolated framework-managed worktree. With the default
global configuration, its layout is:

```text
~/.dev-orchestration/worktrees/<project-name>/<run_id>/
```

The base checkout is not the implementation worktree. Inspect the current run
with `dev-orch status <run_id>` and list local runs with `dev-orch runs`.

Framework-owned evidence is stored under:

```text
.ai/runs/<run_id>/
├── manifest.json
├── events.jsonl
├── planning/
├── review/
└── verification/
```

The run may also contain execution and approval artifacts. Inspect these files
for handoff, including the manifest, event log, plan versions and approved
plan, review results, validation evidence, and final verification. These
artifacts are framework-owned and remain outside agent modification scope.

## Substantial workflow controls

The substantial workflow machine-enforces the following review and verification
stages:

- plan review before execution;
- implementation review against the actual change and validation evidence;
- final verification against the supplied acceptance criteria.

Planning, reconciliation, configured validation, and bounded remediation may
also appear in the run. The `agent_orchestration` profile separately declares
workflow-change review as required and surfaces that requirement to agents, but
workflow-change review is not currently a runtime stage enforced by the tier
engine. When a change affects the orchestration workflow, operators must record
the workflow-change review evidence manually until runtime enforcement exists.

Substantial work does not require human approval by default. If the resolved
policy or an active profile produces `approval_required`, the run halts in
`AWAITING_APPROVAL` before execution. The current CLI has no approval or resume
command; do not treat the halted state as approval and do not invent a resume
path.

## High-risk work and escalation

The `high_risk` tier cannot currently be executed by the framework. Security,
privacy, data, payment, architecture, scope-boundary, and other high-risk
changes must stop and be escalated out-of-band. An explicit organizational
approval does not make a high-risk run executable by the current CLI.

Keep policy approval distinct from framework capability: an organization may
require approval for a change while the framework still refuses to execute or
resume that tier.

## Local-only boundaries

Local commits may be created autonomously only on `ai/`-prefixed branches and
only when otherwise permitted by repository policy. The framework-managed run
worktree is where implementation and the final local commit occur.

Autonomous actions are prohibited from:

- pushing or force-pushing;
- merging or deleting remote branches;
- deploying or publishing;
- mutating production data.

This documentation task does not itself require a commit. Validation gates must
never deploy, publish, mutate production data, or write to a remote system.

## Validation and substantial-run evidence

The configured gates required for substantial work are:

```text
.venv/bin/ruff check --no-cache src tests
.venv/bin/ruff format --check --no-cache src tests
.venv/bin/python -m pytest -p no:cacheprovider
```

Validation runs in the isolated worktree. The framework temporarily exposes the
base checkout's ignored `.venv` when needed and removes that temporary link
after validation; the test command disables pytest's cache provider to avoid
cache residue.

A substantial-run handoff must identify:

- files changed;
- plan, implementation, workflow-change, and final reviews completed,
  distinguishing machine-generated evidence from manually recorded evidence;
- commands run and their results;
- failures, omissions, or skipped checks;
- relevant locations under `.ai/runs/<run_id>/`;
- confirmation that no prohibited remote or production action occurred;
- a documentation-specific scope check confirming that only the intended
  documentation file changed.

For this guide, that final scope check must confirm that the change set contains
only `docs/SELF-HOSTING.md`; no source, test, configuration, protected path,
run artifact, or canonical specification may change.

## Unresolved follow-ups

Track these separately from this guide:

1. Reconcile the declared persistent-context policy with the manifest and
   assembler evidence showing `AGENTS.md` and `.ai/context.md` excluded from
   current context assembly.
2. Add runtime enforcement and durable evidence for workflow-change review, or
   revise the canonical declaration through an approved change.
3. Define an approved operational path for human approval and resumption if
   `AWAITING_APPROVAL` runs are intended to continue.
4. Implement and separately review any future high-risk execution capability;
   approval alone is not sufficient.

These follow-ups do not authorize changes to canonical specifications,
configuration, implementation, or protected paths as part of this documentation
change.
