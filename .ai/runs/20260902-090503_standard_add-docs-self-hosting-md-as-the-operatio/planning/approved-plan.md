## Revised plan

1. Preflight the documentation-only scope.

   - Inspect repository status before editing.
   - Proceed only if the intended change can remain limited to `docs/SELF-HOSTING.md`.
   - Treat `.ai/`, configuration, source, tests, and canonical specifications as read-only evidence.
   - If unrelated uncommitted changes or an accidental out-of-scope modification prevent an unambiguous one-file handoff, stop and report the scope conflict without modifying, stashing, discarding, or working around it.

2. Create `docs/SELF-HOSTING.md` as the sole deliverable.

   Structure it as an operational guide covering:

   - prerequisites and preflight checks;
   - bootstrap;
   - declared project configuration;
   - observed runtime behavior and known gaps;
   - guarded substantial runs;
   - local-only boundaries;
   - validation;
   - evidence and handoff;
   - unresolved follow-ups.

3. Document the bootstrap mechanism as a narrow, pre-run exception.

   - Give the bootstrap form: `dev-orch init --config <prepared-project.yaml>`.
   - State that initialization creates:
     - `AGENTS.md`;
     - `.ai/project.yaml`;
     - `.ai/context.md`.
   - Explain that this occurs outside an orchestrated run solely to establish repository and orchestration policy.
   - Document that `.ai/context.md` is write-once and is not regenerated by `--force`.
   - Require the bootstrap files to be committed before the first self-hosted run begins.
   - State explicitly that this mechanism is not an in-run exemption from scope fences or protected-path restrictions.

4. Separate declared configuration from per-run classification.

   - Record the configured project classification as `internal_operating_system`.
   - Record the active profile as `agent_orchestration`.
   - Describe `substantial` as a per-run tier selected by classification or supplied through `dev-orch run --tier substantial`, not as a `.ai/project.yaml` project setting.
   - Explain that an explicit tier may raise the classification but cannot lower it.
   - Avoid implying that all self-hosted runs are inherently substantial; use substantial as the required workflow for work classified or overridden to that tier.

5. Describe context handling without asserting unobserved prompt inclusion.

   - Present relevant-context-only loading and on-demand plans or specifications as declared context-selection policy.
   - Do not state that `AGENTS.md` or `.ai/context.md` currently reaches agent prompts.
   - Document the current declared-versus-observed gap neutrally:
     - repository policy describes these files as persistent context;
     - the supplied run manifest records `context_included: []`;
     - that manifest records both `AGENTS.md` and `.ai/context.md` as excluded by the scope fence.
   - Identify the manifest and assembler evidence precisely when drafting the guide, without modifying either.
   - Explain that configured fail-closed behavior applies when active profiles provide conflicting values for the same profile control. Do not describe it as general context-source conflict detection.

6. Add an explicit unresolved context-authority follow-up.

   - Record the competing claims neutrally: the declared persistent-context policy versus the runtime manifest and assembler behavior excluding those sources.
   - Do not decide which claim is canonical, redefine context authority, or imply that the runtime gap has been resolved.
   - State that reconciliation requires a separately approved change to the relevant canonical documentation, specification, configuration, or implementation.
   - Keep that future work outside this documentation-only change.

7. Explain how to operate and inspect a self-hosted run.

   - Cover the relevant CLI flow: `doctor`, `init`, `run`, `status`, and `runs`.
   - Include an illustrative substantial-run invocation using `--tier substantial`.
   - Require one or more meaningful `--criterion` values so final verification has explicit acceptance criteria; mention the CLI warning when criteria are absent.
   - Explain that execution occurs in an isolated worktree under the framework-managed worktree location.
   - Point operators to `.ai/runs/<run_id>/` for framework-owned evidence, including:
     - `manifest.json`;
     - `events.jsonl`;
     - `planning/`;
     - `review/`;
     - `verification/`.
   - State that these artifacts may be inspected for handoff but remain outside agent modification scope.

8. Describe substantial workflow controls according to their actual enforcement.

   - Identify the machine-enforced substantial stages, including:
     - plan review;
     - implementation review;
     - final verification.
   - Describe workflow-change review separately as a declared `agent_orchestration` profile requirement surfaced to agents, not as a runtime stage currently enforced by the tier engine.
   - Require operators to capture workflow-change review evidence manually when applicable until runtime enforcement exists.
   - State that substantial work does not require human approval by default.
   - Explain that an `approval_required` result currently halts a run in `AWAITING_APPROVAL`; it does not provide an approval or resume command.

9. Treat high-risk work as unsupported and out-of-band.

   - State that the `high_risk` tier cannot currently be executed by the framework.
   - Require security, privacy, data, payment, architecture, scope-boundary, and other high-risk changes to stop and be escalated out-of-band.
   - Do not imply that explicit approval makes a high-risk run executable.
   - Distinguish policy approval from framework capability: approval may be required organizationally, while the current CLI still cannot execute or resume such work.

10. Define the local-only operating boundary.

    - Explain that local commits may be created autonomously only on `ai/`-prefixed branches when otherwise permitted by repository policy.
    - State that pushing, force-pushing, merging, remote branch deletion, deployment, publishing, and production-data mutation are prohibited autonomously.
    - Clarify that this documentation task does not itself require a commit.
    - State that validation gates must never deploy, publish, mutate production data, or write to a remote system.

11. Document validation and evidence requirements for substantial runs.

    Require these configured gates:

    ```text
    .venv/bin/ruff check --no-cache src tests
    .venv/bin/ruff format --check --no-cache src tests
    .venv/bin/python -m pytest -p no:cacheprovider
    ```

    Require the handoff to identify:

    - files changed;
    - plan, implementation, workflow-change, and final reviews completed, distinguishing machine-generated from manually recorded evidence;
    - commands run and their results;
    - failures, omissions, or skipped checks;
    - relevant run-artifact locations;
    - confirmation that no prohibited remote or production action occurred;
    - a documentation-specific scope check confirming that only `docs/SELF-HOSTING.md` changed.

12. Validate the proposed documentation change.

    - Review the rendered Markdown for usable heading hierarchy, readable commands, clear declared-versus-observed labels, and consistent terminology.
    - Run `git diff --check`.
    - Run all three configured lint, format, and test gates even though they target `src/` and `tests/`.
    - Capture each outcome without altering source or tests to address unrelated failures.
    - Inspect final status and diff to confirm that no source, test, configuration, protected path, run artifact, or canonical specification changed.
    - If the final change set contains anything besides `docs/SELF-HOSTING.md`, stop and report the scope violation.

    - `docs/SELF-HOSTING.md` is an actionable self-hosting operations guide.
    - The bootstrap command, all three generated files, write-once context behavior, pre-run timing, and commit-before-run requirement are explicit.
    - The bootstrap exception cannot be read as a general protected-path exemption.
    - Project configuration is distinguished from per-run tier selection.
    - Declared context policy is distinguished from observed prompt assembly.
    - The context-authority conflict remains explicit and unresolved.
    - Fail-closed behavior is described only for conflicting active-profile controls.
    - Actual substantial stages are distinguished from the declared but non-enforced workflow-change review control.
    - High-risk work is described as unsupported and requiring out-of-band escalation.
    - Approval-required runs are accurately described as halting without a current resume path.
    - Invocation, verification criteria, isolated worktrees, and evidence locations are documented.
    - Local commits are clearly distinguished from prohibited remote, deployment, publishing, and production actions.
    - The final change set contains only `docs/SELF-HOSTING.md`.

14. Recovery.

    - Correct incomplete or inaccurate content only within `docs/SELF-HOSTING.md`.
    - If another file changes accidentally, stop and report it rather than modifying, stashing, discarding, or working around unrelated work.
    - If removal of the new guide is required, use the repository’s approved recovery workflow.
